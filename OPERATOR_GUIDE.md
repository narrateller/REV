# Руководство оператора — версия 1.2.1-candidate

Результат запуска — отдельный проектный каталог и, по выбору, отдельный
GitHub-репозиторий. Эталонный шаблон при запуске не инициализируется и не
перезаписывается. Для разных проектов можно выбирать разные личные аккаунты
или организации GitHub, если действующий аккаунт имеет соответствующие права.

## 1. Подготовить среду и исходные данные

Распаковать архив шаблона в отдельный каталог. Установить Python 3.9+, Git и
Git LFS; для публикации из диалога нужен GitHub CLI (`gh`). Из каталога шаблона:

```bash
python3 -m pip install -r requirements.txt
python3 -m unittest discover -s tests -v
python3 scripts/operator_console.py
```

На Windows вместо `python3` при необходимости использовать `py`.
В интерактивном меню выбрать «подготовить проект». Ввести новый локальный
каталог ВНЕ каталога шаблона, код проекта, название изделия, имя оператора и
каталог материалов. Консоль создаст копию, настроит паспорт, скопирует
источники в sources/raw и запишет их SHA256 в project/source_manifest.json.
Источники не изменяются и не обрабатываются как инструкции.

Скрипт не заполняет ТЗ, не назначает модель и не утверждает ворота. Любой тип
оборудования задаётся свободным текстом; отраслевой профиль и применимые нормы
вырабатываются отдельно. Примеры прессов, дробилок и сепараторов перемещены
в examples/equipment_examples.md; это необязательные примеры, не полный список.

Если материалов пока нет, локальную копию можно создать, но doctor покажет
MISSING. Чтобы добавить их позднее, выбрать пункт 4 или выполнить:

```bash
python3 scripts/operator_console.py add-sources --project <каталог_проекта> --sources <каталог_материалов>
python3 scripts/operator_console.py doctor --project <каталог_проекта>
```

Чтобы отдельно проверить доступ **операторского** GitHub CLI к репозиторию,
добавить `--remote OWNER/REPO`. Проверка запрашивает метаданные от имени текущего
аккаунта; ошибка сети, отсутствие прав и недоступный репозиторий обозначаются
UNKNOWN и не различаются автоматически. Права сторонних моделей она не проверяет.

Повторный файл не перезаписывается. При изменении уже учтённого файла doctor
покажет CHANGED: для замены требуется оформить происхождение и обновить проект
по процедуре изменения, а не незаметно перезаписывать исходный документ. Скрипт
учитывает наличие, размер и хэш, но не проверяет полноту и достоверность буклета.
Если репозиторий уже опубликован, новые источники и обновлённый манифест нужно
отдельно закоммитить и передать через действующую ветку/PR; локальное добавление
само не делает материалы доступными другим моделям.
Перед публикацией пользователь проверяет право размещать документы и выбранную
видимость репозитория. Пароли, токены и ключи в документы не помещать.

## 2. Создать репозиторий в нужном аккаунте

В `gh` войти под нужным пользователем: `gh auth login`; если учётных записей
несколько, переключить `gh auth switch` и проверить `gh auth status`.
Для организации действующий пользователь должен иметь право создавать в ней
репозитории. Переменные GH_TOKEN/GITHUB_TOKEN могут влиять на фактическую
учётную запись; консоль выводит пользователя, возвращённого GitHub API, и
просит ввести его имя для сверки. Не используйте `--show-token` в переписке.

Запустить `python3 scripts/operator_console.py`, выбрать пункт 3, указать
подготовленный каталог, `OWNER/REPO`, видимость и подтверждение с точным именем
репозитория. По умолчанию предложена видимость private. Консоль создаёт локальный
Git, первоначальный commit и новый удалённый репозиторий через gh; она не
редактирует старые репозитории и не делает force-push. Если remote creation или
push оборвутся, проверить фактическое состояние в GitHub и локальном Git до
повтора: удалённый репозиторий мог уже создаться. Автоматического удаления нет.
Если локальный проект уже имеет .git, консоль откажет в публикации; используйте
ваш обычный workflow Git/PR. Альтернатива — создать GitHub-репозиторий вручную
и загрузить подготовленную копию средствами Git, сохранив исходный шаблон.

При запуске из VS Code/другого терминала текущая директория может отличаться:
указывайте абсолютный путь к scripts/operator_console.py. Локальные проверки
не означают, что GitHub Actions уже успешно отработал или что защита ветки
настроена. Правила защиты и обязательного review включаются и проверяются в
настройках выбранного репозитория; до этого enforcement остаётся PROCEDURAL.

## 3. Подключить модель и проверить доступ

Доступ оператора в браузере или GitHub CLI не доказывает доступ модели в ChatGPT,
Claude, Gemini или другой среде. У каждой среды могут быть собственные интеграции
и ограничения на выбранные репозитории. В настройках соответствующего коннектора
или GitHub App дать доступ к нужному OWNER/REPO, в объёме необходимого чтения и
работы в ветке. Способ зависит от среды; для каждой модели выполняется проба.

Первая фраза, если контекст подключения уже указывает на правильный репозиторий:

> Войди в курс дел и текущий статус проекта.

Если репозиторий не задан окружением, добавить его URL и ветку. Модель читает
AGENTS.md, AGENT_PROTOCOL.md, STATE.md, NEXT_MODEL.md и нужные задачи; сообщает
фактический commit, статус, блокеры и предлагает подходящую роль. При запросе
только статуса она не начинает новую роль без действующего назначения.
Чтобы получить фразу с адресом, выберите пункт 5 консоли или выполните
`python3 scripts/operator_console.py message --repo OWNER/REPO --branch main`.

Для проверки чтения попросить модель через её подключение прочитать и сообщить
проект, полный SHA и содержимое project/access_challenge.txt. Сверить ответ с
файлом в целевом репозитории. Случайная строка challenge не является паролем.
Такой ответ — основание для проверки оператором, а не криптографическое
доказательство личности модели или долговременного доступа.

Если требуется запись, модель создаёт ветку access/<session_id>, в ней файл
project/access_probes/<session_id>.md, содержащий только строку challenge, и
публикует ветку. Оператор сверяет её в GitHub. Не удалять чужие ветки и не
обходить защиту основной ветки. Чтение не доказывает запись; запись в ветку
не доказывает право слияния в main или прохождение review.

Для сохранения операторской записи в локальной копии сначала получить историю и
при необходимости ветку `git fetch origin`, затем выполнить:

```bash
python3 scripts/operator_console.py record-access --project <каталог_проекта> --model <название_модели> --session <session_id> --commit <полный_SHA> --challenge <ответ_модели>
```

Для проверки существования полученной пробной ветки добавить
`--probe-ref refs/remotes/origin/access/<session_id>`. Консоль сравнивает
challenge с указанным Git-commit и содержимым локального remote-tracking ref.
Она записывает, что оператор сообщил ответ и что указанный ref был обнаружен
локально; не утверждает, что сама модель владеет доступом или что доступ до сих
пор действует. Запись находится в project/access_receipts/ и относится к одной
сессии. `doctor` показывает такие записи; без них доступ NOT_VERIFIED.
Для ветки, находящейся только в удалённом connector и не доступной локальному Git,
проверка остаётся операторской — нельзя представлять её как машинно выполненную.

## 4. Передать работу следующей модели

При завершении каждой задачи работающая модель обновляет NEXT_MODEL.md и STATE.md,
а при незавершённой работе — Handoff-капсулу. В NEXT_MODEL указываются задача,
статус, известное/неизвестное, проверенные файлы и ревизии, commit результатов,
рекомендуемая следующая роль, точный первый шаг и критерий успеха. Формат:
templates/next_model.md. Самостоятельно другая модель не вызывается: оператор
подключает её в нужной среде и даёт ту же короткую фразу из раздела 3.

Новая модель сверяет проект и commit, затем читает актуальную эстафету. Если
она устарела, ветка недоступна или результаты остались только локально, модель
сообщает об этом и предлагает восстановление из последнего доступного commit.
Нельзя обещать передачу работы, которая не была сохранена/опубликована.
Автор артефакта не становится независимым проверяющим, меняя роль или название
сессии. Назначение следующей модели подтверждается оператором, если оно ещё не
было дано в текущем диалоге.

## 5. Ворота и проверка

Для структурной проверки проекта: `python3 scripts/check_registry.py`. Перед
приёмкой, если есть Git-история: `python3 scripts/check_registry.py --strict --check-git`.
Зелёная проверка не является инженерной приёмкой, не проверяет все неучтённые
числа, реальную независимость модели, настройки доступа или соответствие всем
стандартам. Решения G1/G4/G5 принимает человек; G2/G3 — назначенный R1 в
пределах полномочий либо человек. Нужны реальные доказательства, независимая
проверка и закрытие относящихся к воротам блокеров.

Проектные особенности, не относящиеся к изделию, фиксируются NOT_APPLICABLE с
обоснованием. Зависимости, критерии качества, границы применимости CAD/CAE и
план натурных испытаний выбираются для конкретного оборудования.

## Windows и переводы строк

Для соответствия SHA256 `.gitattributes` сохраняет текстовые файлы без
автоматического преобразования LF/CRLF. Копируйте полный комплект с этим
файлом. Переход со старого шаблона на существующий рабочий репозиторий требует
отдельной проверки доказательств и старых commit: не выполнять `git add
--renormalize` и не переписывать историю автоматически. Если вы только
проверяли шаблон, распакуйте исправленный архив в новый каталог и повторите
`python3 -m unittest discover -s tests -v`.
