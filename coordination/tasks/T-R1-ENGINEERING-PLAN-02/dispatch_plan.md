## Порядок передачи R3 → R4 → R5

1. **R3 — CAE §§4/5/6.** Получи свежую `origin/main` и проверь отсутствие конкурирующих
   владельцев. Заполни [шаблон claim](../T-R3-CAE-456-01/claim_template.json) своим фактическим
   ID, моделью (`UNAVAILABLE`, если точный ID недоступен), SHA `main`, текущим UTC и новым
   lease на 24 часа. Включи как `coordination/claims/T-R3-CAE-456-01.json` в `main` по §3
   протокола. Шаблон хранится в пакете задачи, живое владение оформляет сессия R3.
   После принятия claim проверь ревизии входов, единицы, знаки, точки приложения, связи,
   нагрузочные пути и определяющие допущения. Передай R4 ссылки на case ID и интерфейсы,
   реакции в указанной области, определяющие сочетания, оставшиеся входы и команды
   воспроизведения. Для каждого допущения укажи источник и область применимости.
2. **R4 — W02 CAD.** После передачи R3 зарегистрируй свежий claim и проведи входной аудит
   по точному SHA. Сопоставь предъявленные нагрузки и интерфейсы с опорами, ходами,
   зазорами и закреплениями. При достаточных входах выполни пересборку редактируемой CAD
   и экспорт со сверкой версии инструментов, файлов, хэшей и интерфейсов. По остальным
   входам укажи `UNKNOWN` с причиной и соответствующие `BLOCKED_INPUTS` или `NOT_RUN`.
   Если уточнённая геометрия меняет постановку CAE, зафиксируй затронутые case ID и передай
   их R3 для адресного повторного расчёта до проверки R5.
3. **R5 — независимая верификация.** После передачи пакетов R3 и R4 R1 ставит отдельную
   задачу R5 с точными SHA и путями манифестов. Свежая сессия R5 принимает свой claim,
   воспроизводит проверки, сверяет границы применимости, размерности, балансы,
   граничные случаи и доказательства пересборки W02. Итог фиксируется по каждой области
   и каждому материальному блокеру.

Для каждого handoff укажи точный SHA, пути и хэши входов и выходов, команды,
статусы проверок и остаточные ограничения. Перед включением результатов сверь свежую
`main`, точную голову ветки, owner и lease, отсутствие конкуренции и CI.
В `main` освободи claim при завершении задачи.

## Ограничения и проверки

Оператор утвердил [Design Boundary & Phase Load Envelope v1](../../../cae/cases/design_boundary_phase_load_envelope/README.md)
для расчётов в `ASSUMED_STATIC_SCREENING`. В [постановке R3](../T-R3-CAE-456-01/task.json)
это разрешение записано как `operator_pre_authorized: true`. Входы сохраняют зрелость
`ASSUMED`. Для `UNKNOWN` используй `null` с причиной. Ноль допустим для отдельно заданного
контрольного сценария `ZERO`. Сочетания с `NO_STATIC_EQUILIBRIUM` сохраняют этот статус
и `null` в зависимых результатах. Физическое применение требует подтверждённых
фазовых нагрузок, геометрии, материалов, контактов и граничных условий.
Физические испытания и выпуск КД в производство требуют отдельного решения оператора.

```text
python scripts/check_registry.py --check-git
python -m unittest discover -s tests -v
python verify_output.py --check-git
python cae/cases/T-R3-42-STATES-ENVELOPE-01/verify_output.py --check-git
```
