## R5-CC-B01 — обязательные условия READY не связаны с действием (P1, OPEN)

ready_draft.md определяет READY по material state и всем required_guards target. Но REQUEST_READY — self-loop, не создающий обязательного для действия precondition/epoch token. В contract.json нет связи «действие требует соответствующий READY», а собственные required_guards действий — более узкие множества. Авторский checker проверяет каждую таблицу отдельно и эту связь не проверяет.

Контрпримеры используют **один и тот же контекст**: между проверкой READY и действием состояние/наблюдения не меняются. Все прочие guards явно условно TRUE. Это не передача выдуманного нового события/изменение JSON C, а новые допустимые логические присваивания его существующим определениям.

| Составной случай | READY по C | Правильный исход следующего действия | Фактический classify действия |
|---|---|---|---|
| A_SEGMENT_READY, RECEIVER_DEFINED=UNKNOWN | A-READY-EJECT → INDETERMINATE | A-EJECT → INDETERMINATE, state без изменения | **ALLOWED_ASSUMED → A_EXITING** |
| То же, RESOURCES_READY=FALSE и receiver UNKNOWN | BLOCKED | A-EJECT → BLOCKED | **ALLOWED_ASSUMED** |
| B_BATCH_SELECTED, B_RESET_CONFIRMED=FALSE, RESOURCES_READY=UNKNOWN | B-READY-PRESS → BLOCKED | B-COMPACT → BLOCKED | **ALLOWED_ASSUMED → B_COMPACTED** |
| B_ACCEPTABLE_INITIAL, RESOURCES_READY=UNKNOWN | B-READY-LOAD → INDETERMINATE | B-LOAD → INDETERMINATE | **ALLOWED_ASSUMED → B_RAW_LOADED** |
| B_GATHERED_PARTIAL, RESOURCES_READY=UNKNOWN | B-READY-REFILL → INDETERMINATE | B-REFILL → INDETERMINATE | **ALLOWED_ASSUMED** |
| A_STEADY_LOADED, RESOURCES_READY=UNKNOWN | A-READY-PRESS → INDETERMINATE | A-COMPACT → INDETERMINATE | **ALLOWED_ASSUMED** |
| A_STARTUP_RAW, RESOURCES_READY=UNKNOWN | A-READY-START-PRESS → INDETERMINATE | A-GATHER → INDETERMINATE | **ALLOWED_ASSUMED** |
| B_EJECTABLE, receiver/resources UNKNOWN | B-READY-EJECT → INDETERMINATE | B-EJECT → INDETERMINATE | **ALLOWED_ASSUMED** |

Для A-EJECT отсутствуют PARTITION_DEFINED/RECEIVER_DEFINED/RESOURCES_READY из собственного READY-target; для B-COMPACT — в частности B_RESET_CONFIRMED/RESOURCES_READY; для загрузки/refill также пропущены обязательные target-условия. State label не доказывает актуальность узлов/ресурса, что прямо отмечено в ready_draft.md.

**Почему это блокер:** пакет заявлен как internally consistent вход будущей модели. Сейчас можно получить два несовместимых решения о той же условной операции. Это не ошибка формулы баланса и не доказательство физически опасного выполнения команды; это недоопределённость/несогласованность нормативной связи CYC-01↔CYC-09, которую нельзя передать R4 как уже согласованный контракт.

**Обязательная правка:** явно определить action→READY-target/полный набор предпосылок, выбранный mode/epoch и правила актуальности/инвалидации. Либо применить target-conjunction атомарно при разрешении действия, либо сделать обязательным доказательство READY с проверкой его контекста; standalone self-loop не достаточен. Не требуется физический контроллер или новая CAD для такого исправления документа.

Отдельно различить **разрешение действия** и **регистрацию уже наблюдённого факта**. Если DELIVER_DOSE/COMPACT задуманы только как факты, это должно быть явно отражено в семантике: нельзя игнорировать уже поступившее вещество из-за unready и тем самым потерять массу. Нештатное поступление учитывается с UNKNOWN/fault и запрещает дальнейшее действие, а не выдаёт обычный разрешённый переход. Примеры/трассы должны проверять обе области, не смешивать их словом ALLOWED.

**Критерий закрытия B01:** приведённые восемь случаев и их варианты TRUE/FALSE/UNKNOWN дают ожидаемые BLOCKED/INDETERMINATE без продвижения разрешаемого процесса; известный FALSE доминирует над UNKNOWN. Неактуальный READY не используется повторно; отдельная запись фактического материального события не теряет массу. Положительные условные трассы сохраняются с явными предпосылками. Закрытие только независимым RECHECK нового C; автором не выполнено.

## R5-CC-W01 — возврат A после создания столба (OPEN)

resources_draft.md для startup задаёт восстановление refill-позы **и удержания**. Однако A-STARTUP-RETURN-A_COLUMN_ESTABLISHED не требует RETAINED_STABLE/A_REACTION_DEFINED и не меняет material state. В отличие от обычного A-RETURN, условие удержания здесь отсутствует. При RETAINED_STABLE=UNKNOWN либо FALSE и остальных записанных guards TRUE checker даёт **ALLOWED_ASSUMED**, сохраняя A_COLUMN_ESTABLISHED. Для выбранного H-A ожидаются соответственно INDETERMINATE/BLOCKED, пока сохранность столба не обеспечена.

Уточнить branch-specific предпосылки возврата первого established column и последующего refill. Допустим явно описанный иной способ сохранить/переаудировать материал, но state label не должен автоматически подтверждать удержание. Если условия потеряны, нужен определённый статус неизвестного/неподтверждённого inventory, а не молчаливое сохранение установленного столба. Это документальная проработка Q-R2-03/Q-R3-02 до использования данной ветви, не требование заранее выбрать механизм или доказать реальную силу.
