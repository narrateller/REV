# Интерфейсы CYC-02: базы и последовательности

Схемы NTS (без масштаба) — топология и обязательства проверки, не геометрический
результат. Система O: задняя опорная плоскость камеры на оси прессования;
+x к выходу, +y поперёк, +z вверх. Абсолютное размещение O и offsets UNKNOWN.
Базы D/G — свои плоскости направляющих по y; значения концов UNKNOWN.
Точные длины осевых ходов только baseline_bindings.md/json; новые позиции не
задаются миллиметрами из пикселей. Редактируемые poses.json/permissions.json
содержат все исходные действия checked contract и дополнительные механические
участки; CSV/Markdown — их представление. Имена схем не являются body-level CAD.

| Бункер → D0/D1 дозатор | Доза с entity_id, batch_id и массовой базой | D0 не гарантирует наличие/качество дозы; дозатор-ползун — ASSUMED, не утверждённый механизм |

## A: empty → startup → column → steady

A-AUDIT устанавливает документально пустое состояние только по своим
подтверждениям. FEED-OPEN → LOAD-START (DOSE-DELIVER, FILL-CONFIRM, DOSER-RETURN) →
FEED-ISOLATE → GATHER → STARTUP-RETURN → REFILL повторяются при сохранении
столба, собственной вместимости и реакции. PG_A/PF и число повторов UNKNOWN;
источниковый полный work-stroke не навязывается частичному набору.
A-COLUMN требует отдельного COLUMN_CRITERION, не счётчика ходов.

Steady: LOAD-STEADY → отсечение → APPROACH → WORK в составе COMPACT →
SEGMENT → EJECT → CROSS → RECEIVE → RETURN → NEXT. HOLD/разгрузка/ослабление
зажима до выдачи — пока не определённая физическая последовательность R2/R3;
RETAINED_STABLE требуется на каждом зависимом участке. Готовый сегмент не
создаётся в момент LOAD. Возврат только оси не устанавливает READY.

## B: single и repeated gather

B-AUDIT/RESET должны обосновать начальное состояние. B-LOAD при закрытых упоре
и замке; для B_REPEAT GATHER → GATHER-RETURN → REFILL возвращают тот же batch
с partial inventory, а не создают преждевременный продукт. Вместимость,
сохранение поджатого материала и PF UNKNOWN. B-SELECT отдельно завершает набор.
После FEED-ISOLATE: APPROACH → WORK (COMPACT), затем HOLD-UNLOAD → UNLOCK →
STOP-OPEN в составе B-OPEN-CONFIRM. Эти стадии остаются INDETERMINATE до R2/R3,
не разрешаются из новых времён/скоростей. Затем EJECT → CROSS → RECEIVE →
RETURN → STOP-CLOSE → RELOCK → RESET → NEXT. Принятый продукт и допустимые
остатки проверяются до каждого обратного sweep. RESET_CURRENT — требование
независимого свидетельства, а не следствие команды RESET.

## Guard/evidence и отказы

Каждое исходное действие сохраняет полный список entry/completion из C0c4eb5d.
Механические подстадии связываются с одним родительским действием: START guards
проверяются в его фактическом начале, инварианты — перед каждым зависимым движением. HOLD_CURRENT значит измеренную сохранённую позу с удержанием, не
произвольное место. Неприменимые к режиму действия не доступны; B-GATHER только
B_REPEAT, A-GATHER только A_STARTUP. Общего READY для восстановления не требуется.

Evidence привязано к subject/domain/operation/epoch и ревизиям material/geometry/
resource/receiver, инвалидируется изменением любого затронутого состояния.
Доказанный блокирующий отказ сохраняется при неизвестности другого условия:
BLOCKED; без такого отказа любой обязательный UNKNOWN/stale/unsupported даёт
INDETERMINATE. ALLOWED_ASSUMED возможно только документально при всех текущих
условных подтверждениях; в этом пакете actual у всех строк INDETERMINATE.
Отказы с устойчивыми ID и исходными доменами независимы; адресное восстановление
не очищает чужие. Все отклонённые operation ID, включая A→B→C→A, сохраняются;
recovery получает новый ID, собственные guards и не требует общего READY.
Helper checked contract сохранён без изменений; новые predicates не реализованы.

## Возможное перекрытие — только гипотезы

Внешний refill бункера при G1 и ходе P, подготовка приёмника, либо вспомогательное
охлаждение могут перекрываться лишь после доказательства независимых sweep,
изоляции и одновременных ресурсов. Сейчас это UNKNOWN, не разрешённая циклограмма.
Движение D при открытом G и ходе P не разрешается гипотезой об экономии времени.
Главная ось использует fixed-budget phase.*; сумма не время всего цикла. Длительности,
P/Q приводов D/G, удержания, разгрузки, приёма и восстановления null, не нули.

## Стыки частичных возвратов

PF не приравнен к P0. Перед полным APPROACH требуется P_HOME_CURRENT; если
partial-return пришёл в иной PF, нужен отдельный непрерывный проверенный PF→P0
с удержанием материала и собственными guards возврата. До его задания подход
INDETERMINATE, скачок запрещён. B-RESET не требует RESET_CURRENT на входе:
его собственные RESTORE_SEQUENCE_DEFINED/RESET_SWEEP_CLEAR/RECEIPT/TOOLS_HOME
и ресурсы разрешают попытку восстановления без общего READY; RESET_CURRENT
подтверждается только после завершения, затем требуется LOAD/NEXT.

## START, инварианты и предварительные движения

permissions.json задаёт parent_action_choices, parent_binding и current_parent_guards
каждой подстадии. FEED-OPEN и FEED-ISOLATE имеют собственные условия: нельзя требовать
уже выполненной изоляции для самого закрытия затвора или общего READY до открытия
подачи. Они только устанавливают предварительную позу; родитель LOAD/COMPACT ещё
не стартовал. Их current_parent_guards сохраняют ledger, inventory, receiver,
ресурсы, feedback и зависимые от режима удержание/реакцию, но не конечную позу,
которую как раз устанавливают.

После START у DOSE-DELIVER/DOSER-RETURN сохраняется свидетельство исходного HOME
в истории одной операции. Дозатор в D1 перед возвратом обязан подтвердить D_DELIVERY_CURRENT,
а не одновременно D0. TOOLS_HOME/FEED_CLEAR/ISOLATION_CONFIRMED не универсальные
инварианты всех инструментов: текущая требуемая поза перечислена в строке и её
extra guards; историческое START не разрешает обойти изменившийся receiver,
ресурс, удержание или отказ. Точное разделение feedback subject/этапов требуется
согласовать с R3; неопределённость даёт INDETERMINATE, не разрешение. Материальный
переход фиксируется только после всех собственных completion и родительского
completion; W02 engine/PLC этой постановкой не реализован.

## Уточнение по OUTPUT R5 — B01/B02/B03

[Полный протокол исправления](../correction/README.md) и cycle_protocol.json
задают обязательную последовательность D0→D1→FILL-CONFIRM→D0→commit LOAD→G1.
FILL_COMPLETE — адресная историческая квитанция именно этой дозы/материала/LOAD
и transfer operation, а не команда, таймер или текущий D1 после возврата.
Каждая подстадия завершает только себя; parent LOAD завершается после D0.
При commit исходный helper меняет MATERIAL/FEED: требуется явный successor
связанный с исходной квитанцией и точным +1 только этих ревизий. Отсечение
требует также LOAD_COMMITTED_CURRENT и FEEDER_SAFE; изоляция/нагрузка неизвестны.

A full APPROACH/WORK/HOLD-UNLOAD существуют только в A_STEADY. Для частичного
startup остаются PG_A/PF и свои условия. STOP-CLOSE/RELOCK B требуют собственных
текущих guards и адресного recovery request; общего DEPENDENCY_VALID на входе
этих стадий нет. Closure fault, причинные dependency и остальные fault IDs
разрешаются отдельно; нормальные NEXT/COMPACT не обходят нерешённые отказы.

W02 и физический READY NO-GO, G1 OPEN; это документальное уточнение, не PLC.
