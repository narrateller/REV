## Запись отказа

`faults` — отображение **fault_id → record**, никогда не guard → строка.
`F-<sha256>` вычисляется из канонического неизменяемого `origin`. Два события
одного guard, включая разные сущности/партии или разные причины одной сущности,
имеют отдельные ID. Повтор той же записи не создаёт второй экземпляр.

| Часть | Поля / правило |
|---|---|
| origin | guard, reason, kind, truth, scope, source operation_id, evidence_id **и копия source evidence**, original revisions, cause_fault_ids. Не переписываются после смены представления или восстановления. |
| scope | scenario_id, variant, mode, subject_kind, subject_id, batch_id, cycle_epoch, basis_id/basis_revision. Subject — идентифицированный объект/набор, к которому относится конкретное условие в сценарии; реальные объекты REV UNKNOWN. |
| Массовая база | MATERIAL требует определённых исходных basis_id и basis_revision. Для других типов в схеме явно задано NOT_APPLICABLE_BY_GUARD_SCOPE; это неприменимость, не догадка о массе и не сравнение null с null. |
| revisions | В origin — версии при фиксации. expected_revisions — подтверждённые текущие версии **того же** субъекта; change_subject добавляет revision_history, не заменяя origin. Изменение чужого представления не обновляет старую запись. |
| status | OPEN / RESOLVED. Успех сохраняет запись, ID, исходную область и evidence; добавляет resolution. Другие записи не удаляются. |
| resolution_attempts | Сохраняются попытки: operation ID, evidence ID, исход/причина. UNKNOWN или чужой адрес не исправляют старый отказ. |

Отсутствующий обязательный адрес/база/ревизия — UNKNOWN. Совпадение двух null
не адресация. Идентификатор и origin проверяются при восстановлении сохранённого
контекста; состояние guard в новом view не подменяет область старого fault.

## Адресное восстановление

`recover(contract, action, context, fault_id, proof)` требует **явный ID**.
Guard name не является адресом. Собственные entry guards аудита, новый operation
ID и подтверждённая история проверяются до применения результата. Общий READY
и уже исправленная цель не требуются для начала соответствующего аудита.

Proof содержит fault_id, guard, target_scope, origin_revisions, текущие revisions,
action/RECOVERY_RESULT, новый operation_id, source/method/evidence_id, value и
покрытие интервала. Target и query должны относиться к исходному субъекту fault;
новый аудит не может заверить другую партию вместо спорной. Исходные версии
указываются явно, а текущие должны соответствовать подтверждённой цепочке именно
этого субъекта. Прямое присвоение новой версии в чужом view не такая цепочка.

| Проверка | Результат / сохранение |
|---|---|
| Чужая/неизвестная сущность, партия, эпоха, база, ревизия либо недостаточное evidence | INDETERMINATE; адресованный fault остаётся OPEN. |
| Известный FALSE собственного условия/результата или открытая обязательная причина dependency | BLOCKED; ничего не закрывается. FALSE доминирует UNKNOWN. |
| Все собственные и адресные условия TRUE | Только указанный fault становится RESOLVED; другие, rejected IDs, факты и inventory refs сохраняются. Это ALLOWED_ASSUMED документального примера. |

Результат evaluate связан с `input_context_hash`; propagate отклоняет результат
другого контекста, а не переносит исходный отказ на новую сущность. Канонический
`decide` атомарно выполняет evaluate и сохранение результата. Чтение evaluate
само по себе не исполняет движение и не сохраняет отказ вместо вызывающего.

## Причинная зависимость

Нештатный штатный шаг создаёт отдельную DEPENDENCY-запись с устойчивым ID и
`cause_fault_ids`, а не один заменяемый dependency bit. UNKNOWN-зависимость
остаётся UNKNOWN; известное нарушение — FALSE. Уже существующий отказ не
переписывается под текущую область при следующей попытке.

RECONCILE_HISTORY адресуется к конкретной dependency и требует RESOLVED всех её
обязательных причин плюс собственное адресное evidence истории. Неизвестная или
отсутствующая причина не считается исправленной. Чужая свежая бумага не снимает
исходный материальный отказ. Сверка одной dependency не очищает другие; новые
READY и зависимые действия снова проверяют полный набор, включая DEPENDENCY_VALID.

## Накопительная память ID и отсутствие тупика

В сохраняемом контексте `rejected_operation_ids` — накопительный набор, а
`rejected_operations` сохраняет записи причин под устойчивыми rejection ID.
BLOCKED/INDETERMINATE после decide/восстановительной попытки потребляют ID как
отвергнутый. A→B→A и A→B→C→A всегда отклоняют повтор A, даже после смены
субъекта/эпохи/успешного восстановления других записей и при новом обычном TRUE.
Новый действительно уникальный ID может начать адресный аудит по его условиям.

Чтобы не создать тупик после отвергнутого запроса, RECONCILE_HISTORY отдельно
может **подтвердить обработку** REQUEST/EVENT_FRESH fault: proof указывает
DENIED_REQUEST_ACKNOWLEDGED, исходный denied_operation_id и его rejection records.
Это may_acknowledge, **не** may_reestablish истинности старого EVENT_FRESH. Старый
ID остаётся навсегда rejected, исходный факт отказа не меняется. Затем можно
адресно сверить зависимость и начать новое действие с новым ID, если остальные
условия истинны. Никакого очищения общей памяти или чужих fault при этом нет.

## Сохранение и восстановление контекста

export_context сохраняет весь payload (все fault, resolution, rejected IDs,
факты, inventory refs) и digest. restore_context требует отдельно доверенный
expected_sha256: пересчитанный вместе с изменённым snapshot локальный hash сам
по себе не подтверждает историю. Без доверенной привязки history_confirmed=false;
новый view не получает чистую историю и ALLOWED_ASSUMED. Известный rejected ID
продолжает блокировать даже при неподтверждённой истории. initialize_history
разрешён лишь для явно аудированной новой истории, не для сброса старой.

Здесь нет долговечного сервера/контроллера или защиты от произвольной подделки
входных доказательств. Это проверяемый документальный интерфейс и модель сохранения
метаданных. Потеря истории/канала аудита требует достоверного внешнего входа,
а не вымышленного READY. Реальные пороги/датчики/физика UNKNOWN.

Наблюдённая доза после отказа остаётся в pending_observations с неизвестной
mass_record; повтор факта не зачисляется второй раз, конфликт сохраняется.
Полноценный entity-level material engine, преобразование raw→compacted и
физический баланс **W02 не реализованы**. Расчёты/CAD/rebuild/испытания NOT_RUN.
