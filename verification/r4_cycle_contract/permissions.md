# Разрешения, текущие доказательства и восстановление — редакция 2

**ASSUMED_INTERFACE_PROPOSAL / DOCUMENTARY_ONLY.** Коррекция по
REV-R5-R4-CYCLE-CONTRACT-01-001 на d99afb4c3231d641d4a4921f39987264ce5ffc23.
Это контракт будущей модели, не контроллер/физический material engine. Реальные
значения guards/порогов/ресурсов UNKNOWN. Положительные примеры — только явно
ASSUMED контексты. R5-CC-B01/W01/W02 остаются OPEN до независимого решения.

## Разрешение действия, завершение и наблюдение — разные операции

1. **Запрос старта** проверяет `entry_guards` конкретного действия в его
   `variant/mode/state/epoch`. В них атомарно включены **все** условия указанного
   `ready_bindings` target плюс собственные условия действия. Сам REQUEST_READY —
   чтение, не сохраняемый разрешающий бит. Вызывать его заранее не обязательно;
   обойти его условия отдельным действием невозможно. Пример: A-EJECT требует
   PARTITION_DEFINED, RECEIVER_DEFINED, RESOURCES_READY и остальные условия
   A-READY-EJECT; B-COMPACT — также B_RESET_CONFIRMED из B-READY-PRESS.
2. **Commit завершённого разрешённого шага** требует `required_guards = entry ∪
   completion`: доказанные условия старта/обязательного интервала и отдельное
   подтверждение результата. `ALLOWED_ASSUMED` такого commit меняет только
   предусмотренную фазу условного примера. Старт COMPACT не требует заранее
   готового продукта: COMPACTION_CRITERION относится к completion, до него
   B_BATCH_SELECTED сохраняется. Аналогично DOSE_DELIVERED, TOOLS_HOME и
   B_RESET_CONFIRMED — результаты соответствующих действий, а не циклические
   предпосылки их старта. Они могут быть entry других зависимых действий.
3. **Фиксация факта** не выдаёт разрешение задним числом. При фактически
   поступившей дозе после BLOCKED/INDETERMINATE она записывается с entity/dose ID,
   mass_record и происхождением в pending_observations для обязательной сверки.
   Старый запас и неизвестные массы не исчезают. Оценка material state становится
   UNCONFIRMED; обычная фазовая цепочка не продвигается как разрешённая.
   Неизвестные данные остаются null. Повтор ID — ссылка без второго зачисления;
   конфликтующий payload того же ID сохраняется как fault, не молча заменяется.
   Неподдерживаемый факт сохраняется для сверки без обычного успешного перехода.

Полные sets каждого действия, включая startup/refill/возвраты и восстановление,
даны в [action_conditions.md](action_conditions.md) и contract.json. События
DELIVER_DOSE/COMPACT в таблице переходов означают **commit разрешённого шага**;
они не единственный способ записать уже наблюдённый материал. Физическое действие
с неизвестной предпосылкой не разрешается этой записью факта.

## Что считается текущим подтверждением

Каждое evidence имеет value TRUE/FALSE/UNKNOWN, evidence_id, source/method,
scenario_id, variant, mode, cycle_epoch, subject_id (именно выбранное множество
вещества/интерфейс), operation_id, action, phase и subject revisions. Фаза —
ENTRY либо COMPLETION; результат восстановительного аудита — RECOVERY_RESULT.
Подтверждение должно явно покрывать требуемый интервал операции, включая
непрерывность. Подтверждение другого action/объекта/режима/эпохи/фазы не подходит.

`guard.evidence_domains` задаёт зависимости: материал/подача/ось/удержание/
B closure/выход и приёмник/гидравлика/ресурсы/канал evidence. Revisions — точные
целочисленные ID наблюдаемой версии, не время или параметр REV. Изменение любой
зависимости делает старое TRUE неприменимым → UNKNOWN. Любая перемена доступности
обязательного потребителя повышает RESOURCES revision, не только изменение насоса;
новое потребление/ветвь должны входить в ресурсное основание именно этого действия.

Изменение материала/позы/приёмника, новый факт, вмешательство, потеря обратной
связи или смена mode/epoch требуют переоценки затронутых условий. Поля
`invalidates_on_commit` перечисляют последствия каждого шага. Смена scope всегда
делает старое evidence неприменимым. Чтение READY не продлевает срок и не обновляет
revision. После ожидаемого движения нельзя просто перенести старое TRUE на новую
версию: нужно новое основание, покрывающее результат/интервал. Численные окна
допустимой давности, датчики, пороги и реальные методы REV UNKNOWN; отсутствие
такого окна не означает бессрочную применимость.

## Распространение отказов и UNKNOWN

| Условие | Разрешение / последствия |
|---|---|
| Любое обязательное текущее FALSE, известная ошибка state/mode | BLOCKED; обычный эффект шага не применяется. Известная причина фиксируется как открытый fault. |
| Обязательное UNKNOWN/отсутствующее/устаревшее evidence без известного FALSE | INDETERMINATE; обычный эффект не применяется, зависимость остаётся неразрешённой. |
| FALSE вместе с UNKNOWN | BLOCKED; неизвестность не отменяет доказанное нарушение. |
| Все условия TRUE | Только ALLOWED_ASSUMED в явном условном примере, не реальное разрешение REV. |

DEPENDENCY_VALID требует подтверждённой истории обязательных предшественников.
После отказа/неопределённости последующее действие не получает новый допустимый
state автоматически. Если фактическое изменение уже произошло, оно фиксируется
отдельно; история становится предметом сверки. Нельзя восстановить разрешение
присвоением следующего state, HOME, другим action ID или прежним READY.

Открытый известный отказ **не стареет в разрешение**: он сохраняется отдельно
от истёкшего положительного подтверждения. Новое обычное TRUE не сбрасывает
fault; требуется адресное восстановление с новым основанием. Потеря удержания A
или неизвестный retained inventory снимают подтверждённость material assessment:
UNCONFIRMED, с сохранёнными entity/inventory refs. A_COLUMN_ESTABLISHED как старый
declared label не доказывает ни RETAINED_STABLE, ни COLUMN_CRITERION. Возврат
первого столба требует RETAINED_STABLE **и** A_REACTION_DEFINED. Partial startup
требует STARTUP_INVENTORY_PRESERVED без выдуманного established column.

Отказ EVENT_FRESH относится к конкретному отвергнутому operation_id: этот ID
не становится допустимым после смены эпохи. Новый уникальный запрос аудита может
получить своё основание; это не очистка физического/материального дефекта.
Конфликтующий material/event ID дополнительно оставляет LEDGER_VALID fault до
идентификационной/массовой сверки. Полные адресуемые цели аудитов перечислены
в `recovery_actions.may_reestablish`: например, REASSESS_MATERIAL может сверить
LEDGER_VALID/BASIS_DEFINED/partition, но не исправляет потерю вещества одним
сбросом бита. Требуется новое предметное основание именно спорной сущности/базы.

## Восстановление без общего READY

| Действие | Собственные предпосылки и результат |
|---|---|
| RECHECK_RECEIVER / RECHECK_RESOURCE | EVENT_FRESH, AUDIT_CHANNEL_READY, RECOVERY_METHOD_DEFINED для выбранной проверки. Не требуют исправного приёмника/ресурса заранее. Новый результат UNKNOWN не подтверждает цель. |
| REASSESS_MATERIAL / A_RETENTION / B_CLOSURE | Те же условия применимого аудита; не требуют INVENTORY_KNOWN/RETAINED_STABLE/B_RESET_CONFIRMED заранее. Чтение не двигает тела и не превращает неизвестное в истинное. |
| REACQUIRE_FEEDBACK | Доступен предусмотренный независимый канал получения/проверки evidence. Не требует прежнего FEEDBACK_VALID как входа; отказ самого канала оставляет запрос неразрешённым. |
| RESTORE_B_CLOSURE / старт B-RESET | EVENT_FRESH, BASIS_DEFINED, LEDGER_VALID, CONTINUITY_CONFIRMED, FEEDBACK_VALID, TOOLS_HOME, RECEIPT_VALID, RESET_SWEEP_CLEAR, METHOD_SUPPORTED, RESOURCES_READY, RESTORE_SEQUENCE_DEFINED. **Не требует** общего B-READY-LOAD или уже истинного B_RESET_CONFIRMED. |
| Завершение B-RESET | Дополнительно новое подтверждение B_RESET_CONFIRMED и непротиворечивое основание всего восстановления. До этого B-COMPACT и следующий batch не разрешены. |
| RECONCILE_HISTORY | Собственный применимый аудит. Закрывает DEPENDENCY_VALID только при новом scoped evidence и отсутствии других открытых известных причин; не амнистирует потерянный материал/незакрытый B. |

Аудит только позволяет запросить evidence; реальное движение требует своих
поз/clear/ресурсов/метода и отдельного подтверждения завершения. Даже успешный
аудит одного условия не даёт всем следующим действиям TRUE: они проверяют свои
текущие входы. Возможный путь восстановления B: разрешённый reset → новое
подтверждение closure → сверка истории/материала → собственные условия B-NEXT →
новый B-READY-LOAD. Если clear или ресурс неизвестен, reset не разрешён; остаётся
доступный аудит либо UNKNOWN до новых данных. Это отсутствие основания, а не
требование уже выполненного конечного READY для попытки восстановления.

Если отсутствует сам применимый канал/метод аудита, контракт не выдумывает путь
восстановления: требуется достоверный внешний вход/исправление интерфейса с новой
оценкой. В рамках этой задачи такие реальные данные/действия не получаются.

permission_examples.py и check_fix.py исполняют только эти логические примеры.
Они не измеряют материал, не вычисляют нагрузки/энергию, не двигают CAD и не
реализуют журнал установки. Восстановительный алгоритм, физическое открытие B,
полный цикл и безопасность не подтверждены. G1 OPEN.
