## R5-CI-B01 — завершение загрузки, позы и parent binding

**OPEN, P1, R4 с согласованием R2/R3.** Требуется согласовать машинно-читаемые
строки и текст до передачи как стабильного интерфейса CAD.

1. **Текущая D1 и возврат в D0.** A-LOAD-START/A-LOAD-STEADY/A-REFILL и
   B-LOAD/B-REFILL завершаются по `D_DELIVERY_CURRENT`, то есть текущему D1.
   Их DOSER-RETURN имеет завершение `D_HOME_CURRENT`, то есть текущий D0, и
   привязан к тому же parent; общая completion_rule требует parent completion
   вместе с extras. Если parent фиксируется после включённого возврата, ни D0,
   ни D1 не удовлетворяет двум текущим свидетельствам одновременно. Пять
   независимых symbolic-проверок показывают эту несовместимость.
   Если предполагался commit LOAD в D1 **до** возврата, нужно явно определить
   post-commit движение/его operation ID, связь с завершённой дозой и момент
   передачи контекста. Либо завершать parent после возврата с **историческим
   адресным** witness передачи дозы и текущим D0, без требования текущего D1.
   Историческое START HOME уже выделено; для completion такого различения нет.
2. **FILL_COMPLETE.** Имя нового guard не обязательно, но его семантика обязана
   быть однозначна. DOSE_DELIVERED относится к parent completion; у FEED-ISOLATE
   нет явного адресного подтверждения завершённой передачи той же дозы/batch/epoch.
   Предшественник указан только текстом, current_parent_guards относится уже к
   следующему PRESS parent. D0 и свободная в текущий момент плоскость отсечения
   сами по себе не доказывают завершение всей передачи/учёта дозы.
   Нужна явная связь с успешным LOAD/REFILL completion/receipt и правилами
   invalidation либо формальное доказательство её вывода из состояния parent.
   Это пробел спецификации, не доказанный запуск затвора раньше времени.
3. **FEEDER_SAFE / ISOLATED.** D_HOME_CURRENT + подтверждённый безопасный sweep,
   удержание и P_FEED_CLEAR — необходимая предметная база FEEDER_SAFE;
   D0 без валидного удержания/полного пути недостаточен. G_ISOLATED_CURRENT
   заявлен сильнее имени G1; для PRESS сохранён ISOLATION_CONFIRMED. Их scope,
   источник, устойчивость отсечения под материалом/нагрузкой и преобразование
   completion затвора в актуальный PRESS entry должны быть согласованы R2/R3.
   Новый физический сигнал не реализован; UNKNOWN не разрешает движение.
4. **Режимы.** A-MECH-APPROACH, A-MECH-WORK, A-MECH-HOLD-UNLOAD объявлены и
   для A_STARTUP, но их единственные parent A-COMPACT/A-EJECT доступны только
   A_STEADY. Корректное parent binding отклонит такой режим, однако строка
   противоречива. Убрать лишний режим либо добавить реальный отдельный startup
   parent/позы/условия без подмены частичного PG_A полным рабочим ходом.

Закрытие: исправленные JSON/MD/SVG/CSV и явная трасса D0→D1→D0→G1→P с
адресным FILL_COMPLETE, invalidation и независимым RECHECK. Отдельно проверить
провал/UNKNOWN completion и повторный набор с сохранением остатка.

## R5-CI-B02 — B reset recovery и generic dependency

**OPEN, P1, R4/R3.** Родитель B-RESET сохраняет checked условия и не требует
DEPENDENCY_VALID, но B-MECH-STOP-CLOSE и B-MECH-RELOCK добавляют его через общий
набор own entry. В условном контексте с известным неразрешённым dependency при
всех остальных корректных reset-входах parent может начать восстановление,
а обе дочерние стадии BLOCKED. Этот исход воспроизведён с настоящей
latched dependency неизменённого checked helper: отказ B-NEXT по
B_RESET_CONFIRMED → новый B-RESET ENTRY ALLOWED_ASSUMED →
DEPENDENCY_VALID остаётся FALSE для механических подстадий. Отдельной связи этих механических движений с
RESTORE_B_CLOSURE или адресным восстановлением fault не представлено.

Нужно явно разделить самостоятельное безопасное восстановительное движение
и штатный reset, определить scope причин, которые действительно запрещают
восстановление. Проверить положительный путь: fault → новый адресный recovery
без общего READY → текущий результат closure → отдельная сверка history →
свежие условия NEXT. Не удалять DEPENDENCY_VALID глобально и не очищать
неисправленные материальные/сервисные причины. Это новая несогласованность
refinement; **B01 прежнего helper на C0c4eb5d не переоткрывается**.
