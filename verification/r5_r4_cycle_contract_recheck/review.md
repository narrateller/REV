## Что исправлено и где ограничения соблюдены

Прямой обход READY исправлен: A-EJECT с неизвестным приёмником/ресурсом,
B-COMPACT с невосстановленным B, загрузка, повторный набор и прессование
теперь не получают ALLOWED_ASSUMED при потере соответствующего условия.
FALSE вместе с UNKNOWN даёт BLOCKED. Чтение READY не заменяет специфическое
evidence действия. Старые required guards не удалены.

Проверены смена batch/subject/operation/scenario, неверные variant/mode/state,
устаревание MATERIAL/AXIS/EXIT_RECEIVER/RESOURCES/HYDRAULIC revisions.
Старое evidence даёт INDETERMINATE; известный отказ приёмника сохраняет BLOCKED
после устаревания и при неизвестном ресурсе. Текущий запрет приёмника не скрывается
другими устаревшими подтверждениями после смены партии.

ENTRY и COMMIT разделены: начать условное формование можно без уже готового
COMPACTION_CRITERION, но commit без него INDETERMINATE и не создаёт изделие.
Частичный B reset с неизвестным итоговым B_RESET_CONFIRMED не продвигает цикл;
с неизвестным ресурсом не разрешается даже старт движения. Компонентные наблюдения
в fixture не заменяют подтверждение всей цели: агрегирование реальных сигналов
и достаточность метода остаются UNKNOWN.

Восстановление B не требует уже достигнутой цели или общего READY. Условный
полный путь проверен: известный отказ B-NEXT → собственный аудит B_CLOSURE →
новое адресное подтверждение той же сущности → RECONCILE_HISTORY после устранения
причины → свежие условия B-NEXT. Неизвестный результат аудита сохраняет отказ;
преждевременная сверка истории блокируется другим открытым отказом. Неизвестный
канал аудита не выдумывает восстановление. После успешной сверки неизвестный
ресурс новой B-LOAD всё ещё даёт INDETERMINATE. Это исключает показанный
логический круг при условных исправных входах, но не доказывает наличие
реального канала или физического способа восстановления.

Наблюдаемое поступление после неразрешённой загрузки сохраняется в pending queue
с identity и неизвестной mass_record, без нулевой массы и разрешения задним
числом; inventory refs и фаза сохраняются. Повтор факта не даёт второго
зачисления, конфликтующий payload сохраняется и фиксирует LEDGER_VALID fault.

## R5-CC-B01: незакрытые обязательные исправления

**OPEN, P1.** Прямые READY bindings исправлены, но требование адресности и
сохранения отказов в меняющемся контексте ещё нарушается. Это дефекты
документального примера и согласованности контракта, не доказанные дефекты АСУ
реального пресса.

### 1. Подтверждение другого материала снимает старый отказ

Минимальная цепочка из независимого JSON:

1. A-RECEIVE для `material-1`, `batch-1`, с текущим LEDGER_VALID=FALSE
   даёт BLOCKED. `propagate` сохраняет LEDGER_VALID и DEPENDENCY_VALID faults.
2. В том же сохраняемом контексте, включая `inventory_refs=['material-1']`,
   задаётся аудит REASSESS_MATERIAL с новым operation ID для **другого**
   `subject_id='unrelated-material-2'`, `cycle_epoch='batch-2'`.
   Его evidence полностью текущее для нового материала, но ничего не утверждает
   о спорном `material-1`. Нет операции сверки/передачи или связи этих сущностей.
3. `recover(... LEDGER_VALID, new_subject_proof)` возвращает
   **ALLOWED_ASSUMED** и удаляет старый материальный fault.
   Правильно: результат по чужой сущности не закрывает этот отказ;
   **INDETERMINATE с сохранением LEDGER_VALID** для предъявленной попытки.
4. Следующий RECONCILE_HISTORY также даёт **ALLOWED_ASSUMED**, очищая dependency.
   При неразрешённом исходном материальном отказе ожидается **BLOCKED**.

Случаи `different_material_proof_cannot_clear_old_ledger_fault` и
`history_must_retain_unresolved_original_material_fault` — два FAIL.
Причина: `latch` хранит материальный fault лишь строкой под ключом guard;
`recover` проверяет record относительно **нового** context и затем выполняет
`faults.pop(guard)`. Исходная предметная область отказа не сравнивается
(permission_examples.py, строки 27–31 и 135–154).
Это противоречит `failure_scope` в contract.json и permissions.md: восстановление
должно иметь основание именно для спорной сущности/базы.

Необходимо сохранять идентичность и область исходного отказа, адресовать
результат восстановления к конкретной открытой причине и сохранять другие
материальные отказы при смене партии/состояния. Новый аудит/эпоха сами по себе
разрешены; требование — явная связь с прежней спорной сущностью, а не вечный
запрет на смену эпохи. Добавить положительные проверки законной адресной сверки
после смены версии и отрицательные проверки другой партии/материала и нескольких
одновременно открытых причин.

### 2. Второй отвергнутый operation ID вытесняет первый

REASSESS_MATERIAL с `operation_id='rejected-A'`, EVENT_FRESH=FALSE даёт BLOCKED;
результат реально передан в `propagate`. Затем аналогично отклоняется
`rejected-B`. После этого попытка снова использовать **rejected-A**, снабжённая
новыми обычными evidence, получает **ALLOWED_ASSUMED на ENTRY** вместо BLOCKED.
Это случай `earlier_rejected_ID_must_not_be_forgotten`.

`faults['EVENT_FRESH']` содержит единственный ID, B перезаписывает A;
`active_fault` помнит лишь последний (строки 19–31). Остаточный DEPENDENCY_VALID
не блокирует собственный запрос аудита — и не должен служить заменой памяти
отвергнутого ID. Политика явно запрещает повтор отвергнутого operation_id,
в том числе после смены эпохи. Нужна сохраняемая история/множество отвергнутых
ID в определённой области, с проверками A→B→A и составных отказов. Новый
действительно уникальный ID должен оставаться пригодным для аудита — этот
положительный случай уже независимо подтверждён, общего тупика создавать нельзя.

Для закрытия B01 необходимы исправленный C, согласованные текст/JSON/helper,
контрпримеры с указанными правильными исходами и новый независимый RECHECK.
Один лишь успех существующих 154 checks недостаточен.
