# AGENT_PROTOCOL — OPERATOR FORK 2.0

Действует для новых сессий с main после операторского форка 2026-11-18.
Основание: decisions/ARB-OPERATOR-FORK-BASELINE-01.md. Старый протокол и его история
сохранены в archive/context/operator-fork-20261118/; архив не является входом onboarding.
Репозиторий хранит состояние, чат хранит только рабочий контекст текущей задачи.

## 1. Stateless Session Onboarding

Минимальный вход: AGENTS.md → STATE.md → roles/Rn/README.md. Не загружать archive/,
старые handoffs/все reviews/CAD сразу. По task ID из компактной очереди прочитать только
его manifest, точные входы, критерии и выбранные параметры с зависимостями. Ссылка на
непрочитанный источник не означает его проверки. При указанной роли сразу продолжать
её выбранную задачу; повторный Role Handshake не нужен. Если роль не задана, выбрать
незанятую READY-задачу по приоритету и её роли и подготовить новый claim.

Сессия сообщает actual session ID из среды, модель с точным runtime ID либо UNAVAILABLE,
проверенные инструменты и ограничения. Generated run ID не выдавать за actual thread ID.
Недоступные данные/инструменты обозначать UNKNOWN/UNAVAILABLE, не имитировать запуск.

## 2. Ответственность и Context Scope

| Роль | Результат | Область чтения после onboarding |
|---|---|---|
| R1 Координатор | Очередь, claims, интеграция, решения/приёмка | coordination/, решения, manifests и итоговые отчёты; не все исходники других ролей |
| R2 Данные/Референсы | Точные исходные данные и применимость/неопределённость | sources/, process/, scoped R2 baseline, нужные registry entries |
| R3 Инженерные расчёты | 42 нагрузочных состояния, §§4/5/6, прочность/устойчивость, cae/ и drives/ | params/, 42-state catalog, R2 input package, R4 interfaces/geometry manifests, cae/, drives/ |
| R4 CAD/КД | cad/, W02 CAD-rebuild, drawings/, интерфейсы/допуски | cad/, drawings/, params/, выбранные R3 нагрузки/реакции и данные R2 |
| R5 Верификация | Независимая инженерная проверка и CI-воспроизводимость | manifest проверяемого результата, его входы/код/evidence и tests/; без полной истории |

Матрица применяется вперёд. Старые подписи R1–R6, роли и акты не переименовываются.
Каждый результат имеет author_sessions. Автор не выдаёт свою проверку за независимую.
R5 проверяет численную корректность/размерности/балансы/границы/сходимость и результаты,
а не запускает многораундовый спор о редакции текста. Прежнее upstream-участие раскрывается.

## 3. Новые claims и конкурентная работа

Все старые locks сняты оператором. Исходные claims/tasks/scopes сохранены побайтно в
coordination/completions/operator-fork-20261118/; их старые ACCEPTED/lease поля — история,
не полномочия. Старые UUID не получают автоматически новые задачи или продление.

Новая сессия создаёт coordination/claims/<task_id>.json: task_id, role, owner_session (actual session ID),
model_label, source main SHA, input manifest, proposed_at_utc, lease_expires_at, status.
Для нового предложения по умолчанию 24 часа от UTC подготовки, если оператор не задал иной
срок. Это новый lease, а не перенос старого. До последовательного принятия в main —
PROPOSED; после main inclusion/проверки единственного владельца — ACCEPTED_MAIN.
Роли/задачи операторской READY-очереди предварительно разрешены. Новый исполнитель
может сам последовательно включить свой claim обычным fast-forward push из свежей main
или normal PR merge после проверки единственного владельца; отдельный чужой чат для
подтверждения роли не нужен. Push при гонке отклоняется без force, затем перечитать main.
Это принятие владения задачей, не самоодобрение инженерного результата. R1 ведёт очередь.
Один исполнитель владеет одной задачей. Проигравший гонку сохраняет отдельную ветку и
перечитывает main. После истечения/освобождения прекращает интеграцию; recovery требует
явной записи нового владельца/срока, автоматического присвоения и renewal нет.

Рутинные исправления в пределах принятой инженерной задачи используют тот же claim.
Для косметики/renderer/редакции формулировок не создавать scope_amendments и новые PR
на разрешение recheck. R1 обновляет текущий task manifest/точный target SHA и повторяет
затронутые автопроверки. Расширение инженерной области, изменение требований/риска или
смена owner — отдельное явное решение, а не текстовая косметика.

## 4. Инженерная дисциплина и входной аудит

Числа изделия и критериев хранятся под ID/revision в активном registry или явно названном
scoped dataset со своим commit/hash. Не смешивать R2 scoped 55 с active registry 1144 молча.
Источник/единица/SI-перевод/режим/знак/frame/точка/метод/допуск/неопределённость/зависимости
фиксируются раздельно. UNKNOWN=value:null с причиной; отсутствие допуска не нулевая ошибка.
RAW→ASSUMED→CALCULATED→VERIFIED→LOCKED требует собственных оснований. Operator freeze
не повышает maturity. Буклет BP500 — референс, другие прессы по релевантности; реальные
свойства/реакции и неразрешённые power/pressure/moisture вопросы не угадывать.

Перед инженерным запуском фиксируется аудит точных входов: требования/границы/источники;
размерности/знаки; определяющие зависимости/балансы; геометрия/связи/BC; цикл/ресурсы;
traceability. Недоступная проверка — NOT_RUN. Для отсутствующих определяющих входов
результат BLOCKED_INPUTS/UNKNOWN либо явно ограниченный условный расчёт по зарегистрированным
предпосылкам. Не выдавать условную арифметику за реальную физическую достаточность.

Оператор разрешил переход к запланированным расчётам 42 состояний/§§4/5/6 и W02 новым R3/R4
после fresh claim/input audit, вместо прежнего общего запрета инженерного старта.
G1/ТЗ/архитектура этим не объявлены утверждёнными. Физические испытания и manufacturing
release требуют отдельной команды человека; этот форк их не выполняет и не разрешает.

## 5. Результат, автопроверки и приёмка

Каждый инженерный пакет содержит verify_output.py либо точную эквивалентную команду,
input/output manifest с SHA256/commit, исходники/среду/команды и результат по каждому
критерию. Сначала deterministic checks, registry --check-git и штатный CI. CI проверяет
сохранённые evidence без предварительной регенерации. Replay и независимая проверка
формулы/физики различаются. 42 записи каталога не равны 42 рассчитанным случаям.

R3 для каждого case ID сохраняет CALCULATED в указанной области, BLOCKED_INPUTS,
NOT_RUN или обоснованное NOT_APPLICABLE. Unknown не превращается в ноль/успех, обязательный
случай не исключается ради PASS. Для CAE требуются BC/контакты/материалы/нагрузки,
балансы, предельные случаи и проверка сетки/шага/чувствительности по применимости.
R4 W02 подтверждается actual editable CAD rebuild, геометрией/ходами/интерфейсами,
output hashes и verify_output, а не наличием старых STEP/FCStd картинок.

R5 получает точный target SHA в manifest задачи; исправления в том же scope проверяет
без новых промежуточных scope_amendments. Приёмка опирается на воспроизводимые результаты
и применимые инженерные критерии. Editorial defect исправляется автором и узким тестом;
он не запускает новую цепь утверждения области. Материальный инженерный дефект создаёт
конкретную задачу/блокер с влиянием на результат, а не рекурсивный спор о словах.

Оператор вправе явно принять документальный результат/остаточное ограничение. Такая
запись называется user_authorization/operator decision, не независимый R5 PASS.
OBS01/02/03 закрыты именно так решением ARB-OPERATOR-FORK-BASELINE-01; старые FAIL/акты
сохранены. Новые инженерные результаты этим решением не объявлены рассчитанными.

## 6. Git, компактный контекст и завершение

Работа — в отдельной ветке с base SHA. Перед merge проверить свежие main/exact head,
CI, входы, owner/lease и конкуренцию. Обычные merge согласованных задач заранее разрешены
пользователем; повторное per-PR/per-head согласие не запрашивается. Сохранять историю,
без force/squash/rebase. Конфликты разрешать по смыслу с сохранением источников.

STATE.md — текущие факты/база/блокеры; ISSUES_AND_TASKS.md — только активная компактная
очередь; NEXT_MODEL.md — следующий конкретный шаг/роль/критерий. Не добавлять к ним
полную старую хронологию. Историю сохранять отдельными dated/commit snapshots с хэшами,
а не удалять. Handoff на границе задачи: результат/входы/команды/проверки/остатки и точный
commit. C/H допустимы, но отдельная пара и новый scope PR для каждой косметической
правки не обязательны. После завершения owner освобождает claim в main.

G1 требования/план; G2 реализуемость; G3 CAD; G4 верификация/валидация; G5 КД/готовность
изготовления. PASS только в проверенной области. Выпуск и принятие остаточного риска —
решение человека. Current enforcement PROCEDURAL, пока серверная защита не подтверждена.
